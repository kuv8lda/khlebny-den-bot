# Отклонения от ТЗ

- Пакет называется `khlebny_bot` (не `bot`): запуск через `python -m khlebny_bot.main`, а не корневой main.py.
- Конфиг на этапе 0 содержит только BOT_TOKEN и LOG_LEVEL; параметры панели добавим вместе с интеграцией.
- SQLite-хранилище FSM не входит в этап 0, добавилось вместе с первым сценарием на FSM.

# Отклонения и допущения

- Цены в `khlebny_bot/catalog.py` — временные значения.
- `/cancel` сбрасывает состояние FSM и данные оформления, но не корзину; очистка корзины — отдельная кнопка.
- Количество меняется кнопками «−»/«+» в диапазоне 1–20, а не вводом числа.
- FSM-хранилище SQLite написано на stdlib `sqlite3` через `asyncio.to_thread`, без aiosqlite; репозиторий заказов — так же.
- `httpx` и `respx` не подключены: сети нет, добавим на этапе 3.

# Этап 2

- В `orders` добавлена колонка `checkout_token` (UNIQUE): повторное «Подтвердить» возвращает уже созданный заказ, а не создаёт второй.
- «Заказ + очистка корзины одной операцией» заменено на идемпотентное создание с последующей очисткой: корзина лежит в FSM, а заказы могут быть в другом файле (`ORDERS_DB_PATH`), общей транзакции нет.
- Заказ строится из снимка позиций с экрана подтверждения (хранится в FSM); после оформления корзина очищается целиком.
- Оформление и «Мои заказы» вынесены в `khlebny_bot/checkout.py` с отдельным роутером; в main он подключается после `handlers`, чтобы команды и кнопки меню работали в любом состоянии.
- Дата заказа показывается в UTC с пометкой.

# Этап 4 (отправка заказов в панель)

- `pending_panel_sync` — флаг отложенной синхронизации: `True` если заказ не удалось отправить в панель при создании.
- Дубли по `Idempotency-Key` (200/409) не повторно вызывают панель — обрабатываются как успех с `duplicate=True`.
- `PanelError` при отправке → заказ уже сохранён локально, флаг `pending_panel_sync=True`, пользователь получает нормальный ответ.
- `PanelClient.create_order(payload)` в `panel.py`; 201 — успех, 200/409 — дубль, 422/другое — `PanelError`.
- `panel_client: PanelClient | None` инжектируется в `on_confirm` через aiogram DI; `None` если `PANEL_API_KEY` пуст.
- Новых зависимостей нет. Панель не тронута.

- Настройки панели добавлены в существующий `config.py` (pydantic-settings), отдельного модуля для чтения `.env` нет.
- `httpx` и `respx` уже были в `pyproject.toml`; новых зависимостей нет (строка выше про «не подключены» устарела).
- `BOT_API_TOKEN` в проекте не использовался: `BOT_TOKEN` — токен Telegram, `PANEL_API_KEY` — ключ панели.
- Пустой `PANEL_API_KEY` выключает интеграцию; при сбое панели бот берёт устаревший кэш или хардкод-каталог, повтор запроса — не раньше чем через `CATALOG_TTL_SECONDS`.
- `id` из панели принимается только как целое (строка `"1"` — ошибка формата); дубли `id` — ошибка.
- `panel.py` пока не подключён к `handlers`/`checkout`/`main`: они читают `catalog.CATALOG`.

# Этап 4 — живая проверка

- Проверено вживую: заказ из Telegram → POST /api/integrations/orders → 201 CREATED,
  panel_id получен, в панели заказ с source='telegram', items и amount_cents верны.
- Fallback (панель недоступна → pending_panel_sync=1) — проверить отдельно.
- Панель требует load_dotenv() в app.py, иначе PANEL_API_KEY не читается из .env.

# Этап D (сценарий владельца)

- Телефон в карточке владельца не выводится: бот его не собирает, а хранить больше данных, чем нужно для демо, не нужно.
- Номер заказа в карточке — номер в боте (тот же, что у клиента); id панели лежит отдельно в новой колонке `orders.panel_order_id`, миграция добавляет её при старте.
- Формат PATCH взят из ТЗ и не сверен с панелью: тело `{"status": "<новый>"}`, 200 — успех, 409 — отказ; поле `status` в теле ответа читается, если оно есть. Сверить вживую.
- Для владельца локальный статус `new` равен `pending`; после смены в базе бота хранится статус панели.
- Заказ без связи с панелью (`pending_panel_sync`) приходит владельцу без кнопок, с пометкой.
- `/owner` считает по локальной базе: изменения, сделанные прямо в панели, до этапа E не видны.
- `/owner` не добавлен в меню команд Telegram; чужим отвечает «Нет доступа».
- `OWNER_TELEGRAM_IDS` — строка через запятую, а не JSON-список; неверное значение останавливает запуск.
- Уведомление владельцу уходит после ответа клиенту; его сбой логируется и не ломает оформление.
- `README.ru.md` не создан: `README.md` уже на русском; английскую версию и пару файлов сделаем на этапе H.
- Живая приёмка этапа D (заказ → уведомление → кнопка → статус в панели) не выполнена: нужны токен бота и запущенная панель.

# Этап E (события панели и уведомления клиента)

- Контракт сверен с исходниками панели (без изменений панели): ответ — массив
  `{id, order_id, status, created_at}`, только Telegram-заказы, по возрастанию id.
  Telegram ID в событиях нет: получатель определяется по `orders.panel_order_id`.
- Курсор хранится в `panel_events_cursor` в базе заказов. Курсор и локальный статус
  фиксируются одной транзакцией после отправки; события с id не выше курсора игнорируются.
- Воркер один на базу, первая выборка сразу, далее каждые `EVENTS_POLL_INTERVAL`
  секунд после обработки (по умолчанию 5), пакет до 50 событий.
- Панель/Telegram недоступны: курсор не продвигается за неотправленное событие,
  повтор в следующем цикле. Блокировка бота клиентом — логирование и пропуск доставки,
  чтобы не заблокировать поток всем клиентам.
- Неизвестные локальной базе заказы и неизвестные статусы пропускаются с предупреждением.
  Восстановление связей потерянных/старых заказов этим этапом не реализуется.
- Обновляется локальный статус: изменения из панели видны в «Моих заказах» и `/owner`.
- При остановке выставляется stop-флаг и ожидается завершение воркера, затем закрываются
  клиент панели, SQLite и сессия Telegram. Ожидание интервала прерывается stop-флагом.
- Между успешной отправкой в Telegram и сохранением курсора есть аварийное окно:
  возможен повтор после сбоя процесса. Строгий exactly-once без общей транзакции
  Telegram/SQLite не гарантируется; штатные повторные опросы и перезапуск дублей не дают.
- Живая отправка клиенту не выполнялась; проверки используют HTTP- и Telegram-моки.

# Этап F (приватность)

- Команды подключены до шагов checkout, добавлены в меню и справку.
- Локальные заказы и состав удаляются транзакцией; все FSM-записи пользователя
  удаляются по ключам DefaultKeyBuilder, чужие данные и курсор событий сохраняются.
- Локальное удаление идёт перед запросом панели. При ошибке просим повторить /forget;
  повтор идемпотентен, фоновой очереди нет. События удалённых заказов пропускаются.
- Контракт сверен чтением app.py панели: POST с telegram_user_id, 200 и ok=true.
  Панель очищает имя, телефон и username, но сохраняет ID, комментарии и историю.
  Тексты не обещают полного удаления в панели; панель не менялась.
- updated_at в FSM обновляется при записи состояния/данных, не при чтении.
  Миграция даёт старым записям полный срок. Очистка строго старше 7 дней — сразу
  и каждый час; SQLite-сбой логируется, повтор через час. Stop прерывает ожидание,
  задача завершается до закрытия SQLite. Заказы автоматически не очищаются.
- Сообщения Telegram и резервные копии не удаляются. Уже начатая доставка события
  может завершиться одновременно с удалением; глобальная сериализация действий
  пользователя и воркера событий в этом этапе не вводилась.
- README.ru.md остаётся этапу H: текущий README уже на русском.
- Живая проверка не запускалась; проверки используют HTTP/Telegram-моки.
